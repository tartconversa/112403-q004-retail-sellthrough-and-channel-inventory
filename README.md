# 线下渠道动销识别与压货风险预警

整合经销商收货、区域仓与门店库存、POS 销售、退货、调拨和促销资料的复盘工具。
它回答一个具体问题：**一个区域当期的增长，是消费者真的买走了，还是货从经销商仓库挪到了区域仓或货架？**

所有示例标识与数值均为合成数据，数量单位为件。仅依赖 Python 3.11 标准库，无第三方依赖、无外部脚本、无外部字体。

## 快速开始

```bash
# 用内置演示数据启动（推荐，覆盖所有场景）
python3 -m channelops --data demo --workspace workspace

# 或用最小样例
python3 -m channelops --data samples --workspace workspace

# 浏览器打开 http://127.0.0.1:8000/
```

常用参数：`--host`（默认 127.0.0.1）、`--port`（默认 8000）、`--data`、`--workspace`。

运行测试：

```bash
python3 -m unittest discover -s tests -v
```

## 盯住的四条业务规则

### 1. 同一个 (商品 × 地区) 口径

复盘表的每一行是一个 `(SKU, 地区)` 单元，经销进货、消费者净购买、期末库存、库龄、覆盖天数都在这一行上计算。
四月的经销商进货不会拿去和另一个地区、另一个 SKU 的门店扫码相比。

- 覆盖天数有**两列**：`全渠道覆盖`（门店 + 区域仓）和 `门店覆盖`（只看货架）。
  压货最容易藏在区域仓，只看门店会显得库存很健康。覆盖本身是一个区间（动销是区间）；
  表中给出中位估计，促销资格判定使用最悲观（最短）覆盖，避免用乐观估计放过压货地区。
- 库龄用 FIFO 加权：按收货批次从新到旧覆盖期末库存，报告加权天数与最老批次天数。
  只在库存快照对全部纳入节点完整时计算；若库存早于可见收货历史，则报“—”而不是假装新鲜。
- 一个经销商/区域仓只归属一个地区（按多数下属门店判断），避免同一笔收货在多个地区重复计入；
  跨区服务的仓库会在提示里列出。

### 2. 库存快照缺失时，只给有证据的动销区间

动销 = POS − 退货，并按门店的证据强度分档：

| 证据 | 方法 | 输出 |
|---|---|---|
| 期初与期末库存都有 | `stock-bridge` | 点值（库存桥 = 期初 + 收货 + 调入 − 调出 − 期末） |
| 库存桥与净扫码对不上（超出容差） | `stock-bridge-unreconciled` | 两者之间的区间，并标记漏记事件 |
| 只有期初或只有期末库存 | `bounded-pos` / `pos-floor-only` | 区间或下限，绝不外推成点值 |
| 完全没有库存锚点 | `pos-floor-only` | 只报净扫码下限，标记“不能当作消费者需求点值” |

同期的门店逐笔证据在单元钻取页（点击复盘表里的商品·地区）可见；动销环比只在两期都有上下限时计算。

这是硬约束：**没有快照就不补零**。缺失的门店/仓库进入“待补数据”，并阻断依赖全量库存的指标（覆盖天数、库龄、促销资格）。

`feeds.json` 可以声明 POS 或库存数据源的覆盖区间；未声明时，系统从扫码日期推断，并把晚于期末的扫码缺口单列为提示。

### 3. 调拨只移动库存，不是销售，也不是新进货

`transfer-in` / `transfer-out` 只进入库存恒等式，**不计入**经销进货，**不计入**消费者需求。
接收门店不会因为一笔调拨而产生“新进货”，发出门店也不会因为调拨而产生“销售”。
同量、同日的反向调拨会被识别为一对内部调拨并写入提示；只有单边的调拨会被标为“待确认对方门店”。

### 4. 进货额增长不等于真实动销

复盘页把每个单元按 `进货 / 动销` 从高到低排序，并在比值 ≥ 1.5 时标记“渠道压货”。
比值只有在可比门店覆盖足够、且动销有上限时才计算，否则显示“—”，避免拿半覆盖的分母去比全覆盖的分子。

## 三方确认

复盘口径由三个角色分别确认，各自绑定当时的数据指纹（SHA-256 前缀）：

| 角色 | 确认内容 | 指纹覆盖 |
|---|---|---|
| 渠道运营 | 门店与经销层级关系 | 门店、上级、地区、状态 |
| 财务 | 签收与退货的入账口径 | 进货口径 + 退货处理 + 全部收货/退货事件 |
| 区域经理 | 门店陈列与活动范围 | 促销资料（门店、SKU、起止、折扣） |

- 未确认或确认失效时，页面顶部显示“复盘为暂定口径”。
- 数据或口径一旦变化，旧确认自动变为**失效**（stale），而不是继续显示“已确认”。
- 财务确认前必须先保存入账口径；口径可选“门店收货是否计入进货”“退货是否回库”。
  退货处理会同时影响需求与库存恒等式，两侧始终使用同一口径。

## 补货与承诺

建议数量 = 目标覆盖 + 安全库存 − 现有库存 − 在途订单 − 已向经销商承诺。

- **在途订单**来自 `orders.json` 的 `open_orders`，**已承诺**来自 `commitments`，
  安全库存优先采用 `safety_stock`，缺省按动销天数推算。
- `补报 POS / 退货 / 调拨更正`后，**尚未发出的草稿**会按新证据重算；
  动销证据消失时草稿清零并标注“待补数据”，不会保留一个过期数字。
- **已向经销商发出的采购承诺不重写**：数量冻结，只在“风险原因”列说明
  （动销区间变化、库存变化、重算建议低于已发数量等），并写入审计日志。
- 数量为 0 或待补数据的草稿不能发出。

## 促销资源

只有同时满足以下条件的单元才进入排序：

1. 库存完整、覆盖天数可计算，且处于合理区间（默认 14–45 天）；
2. 消费者净购买有同期可比、且为正增长。

评分 = 动销增长 × 可比较门店覆盖率。**进货额增长只出现在说明文字里，不进入评分**。
库存偏高（覆盖超过阈值）的地区即使进货额大涨，也不会自动获得促销资源。
活动提升只在促销资料标记 `confirmed` 且区域经理确认后归因；未确认的活动列为“待确认活动”。

## 数据格式

数据目录至少包含：

- `stores.csv` — `store,parent,region,state`
- `events.csv` — `event,store,sku,kind,qty,at`，`kind ∈ {receipt, pos, return, transfer-in, transfer-out}`
- `stock.csv` — `location,sku,qty,day`

可选：

- `campaigns.json` — 促销资料数组（`campaign, region, sku, store, starts, ends, discount_pct, confirmed, note`）
- `orders.json` — `open_orders`、`commitments`、`safety_stock` 三个 `{store, sku, qty}` 数组
- `feeds.json` — `{feed: pos|stock, location, sku, start, end}` 数组

空单元格表示数据源未提供。表头必须精确匹配；上传通过界面进行时会先校验表头/JSON，再原子替换，校验失败不会覆盖现有数据。

## 设计与安全说明

- **证据优先**：所有不确定都以区间、下限或“待补数据”表达，不用插值填平。
- **确认可失效**：确认绑定数据指纹，数据变了就退回暂定，避免旧签字背书新数字。
- **更正可追溯**：更正事件是完整替代行，按 `corrected_of` 链接；审计日志记录确认、口径、补报与承诺发出。
- **输入不可信**：文本转义；标识符限字符集；上传限文件名、大小与表头；路径不可由用户指定。
- **Web 安全**：所有 POST 需要会话级 CSRF 令牌；响应带严格 CSP、`nosniff`、`DENY` 框架；默认只监听 localhost。
- **无外部依赖**：不加载外部脚本或字体，图表是内联 SVG 并附同页表格。

## 已知边界

- 库龄基于可见收货批次；更早的库存按最老可见批次计龄，并在缺少完整批次史时把库龄标为未知。
- 调拨配对按“同 SKU、同日、同量、反向”识别；仓库到门店的调拨需在事件表中成对记录。
- 促销归因是活动期与非活动期的日均扫码对比，不是因果推断；非活动期无扫码或活动不在本期时明确报告“不能归因”。
- 只有经销商节点、没有任何门店记录的 SKU 不进入区域复盘行，而是作为“仅有经销商库存”提示列出，
  避免把无法对应消费者动销的发货静默计入。
- 确认与审计存储在工作区文件（JSON/JSONL），适合单实例使用；多实例共享需外部存储。
